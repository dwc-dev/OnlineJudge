# OnlineJudge 项目架构介绍

## 1. 项目概览

这是一个基于微服务架构实现的 OnlineJudge（在线判题）系统，核心能力包括：

- 用户注册登录、权限管理（普通用户 / 管理员）
- 题库管理与在线做题
- 多语言代码判题（Docker 沙箱执行）
- 比赛系统（ACM / OI 两种计分方式、报名权限控制、排行榜）
- AI 助手（代码分析 + 题目上下文对话，支持流式输出）

项目主要由 `Go 后端 + Python AI 服务 + Vue 前端` 组成，后端通过 etcd 做服务发现，使用 MySQL 持久化数据，Redis 做 Token JTI 状态管理。

---

## 2. 技术栈

### 后端（Go）

- 框架：`go-zero`（REST + gRPC）
- 微服务通信：`gRPC`
- 服务发现：`etcd`
- ORM：`gorm`
- 数据库：`MySQL`
- 缓存/状态：`Redis`
- 鉴权：`JWT`（AccessToken + RefreshToken）
- 对象存储：`MinIO`（用户头像）
- 代码沙箱：`Docker Engine SDK`（Go 客户端）

### AI 子服务（Python）

- Web 框架：`Flask` + `flask-cors`
- 大模型调用：`openai` SDK（兼容 DeepSeek API）
- 数据访问：`SQLAlchemy` + `PyMySQL`
- 服务发现：`pyetcd`
- RPC：`grpcio`（调用题目服务获取题目信息）

### 前端（Vue）

- 核心：`Vue3` + `TypeScript` + `Vite`
- UI：`Element Plus`
- 状态管理：`Pinia`
- 路由：`vue-router`
- 网络请求：`axios`
- 编辑器：`Monaco Editor`
- Markdown：`md-editor-v3`
- AI 聊天 UI：`vue-element-plus-x`
- 样式：`Tailwind CSS`

## 3. 整体架构

```text
[Vue Frontend]
       |
       | HTTP (REST)
       v
[Gateway (go-zero REST, :8888)]
   |      |       |        |    \
   |gRPC  |gRPC   |gRPC    |gRPC \ HTTP
   v      v       v        v      v
[User] [Question] [Judge] [Competition] [AI Service(Flask,:6005)]
  :6001   :6002     :6003      :6004
                     |
                     | in-process call
                     v
               [code-sandbox]
                     |
                     | Docker API
                     v
             [oj-c / oj-cpp / oj-java / ... containers]
```

说明：

- Gateway 通过 etcd 发现并调用各个 gRPC 微服务。
- Judge 服务内部直接使用 `code-sandbox` 包，通过 Docker 启动隔离容器执行代码。
- AI 服务是独立 Python 进程，Gateway 对 AI 接口做 HTTP 转发（包括 SSE 流式转发）。

## 4. 后端服务拆解

## 4.1 Gateway（`backend/gateway`）

职责：

- 提供统一 REST API（`/api/v1`、`/api/v1/admin`）
- 做认证鉴权与比赛访问控制
- 将请求转发到对应 gRPC 微服务
- 统一响应封装（`code/msg/data`）
- AI 接口转发（普通 JSON + SSE）

关键中间件：

- `AccessTokenAuth`：解析 JWT + 调用 UserRpc 校验 AccessToken JTI
- `AdminAuth`：管理员权限检查
- `CheckContestAccess`：读取 `competition_id`，调用比赛服务做访问检查
- `RequireContestPermission/Started/Running`：比赛阶段控制
- `BlockDuringCompetition`：比赛进行中禁止使用 AI 功能

---

## 4.2 User 服务（`backend/microservices/user`）

职责：

- 注册、登录、登出、刷新 token
- 用户增删改查（管理员）
- 个人信息更新、密码更新
- Token JTI 管理（Redis）
- 头像上传（MinIO，base64 -> JPEG）

认证机制要点：

- AccessToken：15 分钟
- RefreshToken：7 天
- Redis 存储两类 JTI：
  - `access_token:jti:<user_id>`
  - `refresh_token:jti:<user_id>`
- Gateway 每次认证都会调用 `AccessTokenJTICheck` 做二次有效性校验。

---

## 4.3 Question 服务（`backend/microservices/question`）

职责：

- 题目 CRUD
- 分页检索（标题/难度/标签/可见范围）
- 提供判题配置与测试用例查询
- 维护题目统计：提交数、通过数

数据特点：

- `tags`、`judge_case`、`judge_config` 均以 JSON 字符串落库
- `visible_scope` 支持：
  - `public`
  - `competition_only`

---

## 4.4 Judge 服务（`backend/microservices/judge`）

职责：

- 执行普通判题和比赛判题
- 保存评测记录
- 返回详细执行结果（每个测试点）

判题流程：

1. 通过 QuestionRpc 拉取 `judge_case` 与 `judge_config`
2. 组装 `RunConfig` 调用 `Sandbox.RunCode`
3. 获取每个测试点执行结果，按输出是否精确匹配判定 `accepted`
4. 持久化 `judges.exec_result`（JSON）
5. 更新题目提交数；全 AC 时更新通过数

---

## 4.5 Competition 服务（`backend/microservices/competition`）

职责：

- 比赛 CRUD（管理员）
- 报名（可带密码）
- 题目列表/题目详情访问
- 比赛提交判题
- 统计排行榜
- 访问状态检查（是否有权限、是否开始、是否进行中）

实现细节：

- 比赛题目映射保存在 `competitions.questions`（JSON，元素形如 `{qid, id}`）
- 支持两种赛制：
  - `acm`：题目全测点通过才得 100，否则 0
  - `oi`：按通过测点比例给分
- `password_version` 用于密码更新后使旧报名状态失效。

---

## 4.6 代码沙箱（`backend/code-sandbox`）

支持语言：

- C / C++ / Java / Python / Go / Rust

核心机制：

- 每次判题创建 1 个语言容器（镜像如 `oj-c`、`oj-python`），执行后销毁
- 容器参数：
  - `NetworkDisabled: true`
  - 内存限制（含 swap）
  - 栈限制（ulimit）
  - CPU 核数限制
- 每个测试点用脚本包裹执行：
  - `timeout`
  - `/usr/bin/time -v`
- 从 stderr 解析：
  - 运行时间（ms）
  - 最大内存（KB）
- 根据退出码与输出特征识别：
  - 超时 / 内存超限 / 运行错误 / 栈溢出

---

## 4.7 AI 服务（`backend/microservices/ai`）

提供接口：

- `POST /code/check`：代码问题诊断（非流式）
- `POST /chat`：题目上下文对话（SSE 流式）
- `POST /question/sessions`：获取题目下历史会话
- `POST /session/chat/history`：获取会话消息历史

会话机制：

- 新会话时自动写入 system prompt（包含题目内容）
- 第一轮消息会自动生成会话标题
- 会话/消息存储在 MySQL（`sessions`、`messages`）

注意：

- Gateway 中 `internal/logic/ai/*.go` 为 TODO，当前 AI 功能是由 `internal/handler/ai/*.go` 直接实现转发逻辑。

## 5. 前端模块说明（`frontend/src`）

主要页面：

- `AuthView`：登录/注册
- `QuestionView`：题库列表（筛选、分页）
- `CodingView`：题目详情 + Monaco 编辑器 + 提交判题 + AI Chat
- `JudgeListView`：历史评测记录与详情
- `CompetitionView`：比赛列表、报名
- `CompetitionDetailView`：题目集、倒计时、排行榜
- `CenterView`：个人资料与密码修改
- `SpaceView`：用户空间
- `manage/*`：管理员后台（用户/题目/比赛管理）

前端工程特性：

- 统一 API 封装在 `src/api/modules/*`
- axios 拦截器自动注入 AccessToken，并在 40101 时自动刷新 token 重试
- Pinia `user` store 保存登录态与用户信息
- AI 聊天组件使用 SSE 流读取并增量渲染回复。

## 6. 数据库表结构（按功能）

核心业务表：

- `users`：用户
- `questions`：题目
- `judges`：评测记录
- `competitions`：比赛
- `competition_attendances`：报名关系
- `competition_scores`：比赛得分与 judge 记录
- `sessions`：AI 会话
- `messages`：AI 对话消息

多数模型在服务启动时会 `AutoMigrate`，同时仓库提供了 `backend/sql/*.sql` 初始化脚本与示例数据。

## 7. 典型业务链路

## 7.1 普通判题

1. 前端提交 `code + language + question_id`
2. Gateway 调 JudgeRpc
3. Judge 调 QuestionRpc 获取测试用例/判题配置
4. Judge 调 code-sandbox 在 Docker 中编译运行
5. 逐测试点比对输出并生成结果
6. 保存 `judges` 记录，更新题目统计
7. 返回评测详情给前端

## 7.2 比赛判题

1. 用户先报名（可能需要密码）
2. 请求经过比赛相关中间件校验权限与时间状态
3. 提交代码后 Competition 服务调用 JudgeRpc（`judge_type=competition`）
4. 根据赛制计算题目得分并更新总分
5. 排行榜按总分降序展示

## 7.3 AI 对话

1. 前端请求 Gateway `/ai/chat`
2. Gateway 转发到 Python AI 服务并透传 SSE
3. AI 服务读取历史上下文 + 题目信息，调用 LLM 流式生成
4. 完整回复写入 `messages`，前端实时渲染

## 8. 本地运行要点

运行前依赖：

- etcd（默认 `127.0.0.1:2379`）
- MySQL（各服务配置中的 DataSource）
- Redis（User 服务 JTI 校验）
- Docker（用于判题沙箱）
- MinIO（头像上传，若启用）

主要端口（默认配置）：

- Gateway：`8888`
- User：`6001`
- Question：`6002`
- Judge：`6003`
- Competition：`6004`
- AI：`6005`

启动方式：

- Go 服务可用 `backend/run.py` 一键编译/启动（Windows 下生成 `.exe`）
- Python AI 服务需单独启动（`backend/microservices/ai/app.py`）
- 前端使用 `pnpm dev`

沙箱镜像需提前构建（示例）：

- `backend/code-sandbox/internal/strategies/*/Dockerfile`
- 镜像名需匹配代码中的 `oj-c`、`oj-cpp`、`oj-java`、`oj-python`、`oj-golang`、`oj-rust`

---

## 9. 维护时建议优先关注

- 配置文件中的默认密钥与空配置（JWT/DB/Redis/MinIO/API_KEY）仅适合本地开发
- AI 服务与 Gateway 的实现方式是“handler 直连转发”，后续如果希望统一风格可迁移到 logic 层
- 比赛和题目字段里存在较多 JSON 字符串，变更结构时要同步前后端与 RPC 协议
- 判题结果采用“输出全等比对”，如果未来要支持忽略末尾空白等策略，需要在 Judge 层统一扩展
